# ADR: метаданные и совместимость native v2 → v3

**Статус: принято, 2026-10-19.** Задача #26 (historical issue #26).
Решение реализовано в задаче #40: строгий reader/converter v2→v3, защита исходника через Save As и редакторы всех пяти владельцев метаданных. [Текущее поведение и API](NATIVE-V3.md). Ниже сохранён контракт и различие между исходным v2 и новым v3; исторические доказательства #26 относятся к моменту принятия ADR.

## Решение

Сохраняем существующий native v2 без новых семантических полей. Документация
project/relationship и свойства project/view требуют **native v3**. Не прячем
их в пользовательские свойства, отдельные необязательные файлы или поля,
которые старый reader может проигнорировать. Старый редактор обязан отказать
с понятной ошибкой версии, сохранив исходный файл и открытую модель.

`format: "schemka-project"` остаётся прежним; только внутренний `formatVersion`
равен `3`. Оболочка `.arkita` остаётся `schemka-project-file@1`, поскольку
её массив `{ path, content }` не меняется. Метамодель остаётся
`schemka-archimate4@2`: поля метаданных не являются новой редакцией ArchiMate.
Расширение файла `.arkita` либо ранее использовавшееся `.schemka.json` не
определяет версию содержимого. Текущее правило описано в [NATIVE-V3.md](NATIVE-V3.md); исходная схема сохранена в [NATIVE-V2.md](NATIVE-V2.md).

## Владельцы полей и интерфейс

В таблице перечислены поля метаданных; обязательные ID, типы, метамодель,
ссылки, optional profiles/viewpoints и геометрия сохраняются по действующей
[схеме core](../schemka-model-core/README.md). Столбец v2 фиксирует старую схему; обязательные поля v3 реализованы и проверяются текущим редактором.

| Владелец | Исходный native v2 | Native v3 | Место отображения и редактирования |
| --- | --- | --- | --- |
| `project` | Обязательное `name`; `documentation` и `properties` запрещены | Сохранить `name`; добавить обязательные `documentation: string`, `properties: Record<string, string>` | Модель → Свойства модели. Поля принадлежат всей модели, а не активному виду |
| `element` | Обязательные `name`, `documentation`, `properties` | Без изменения | Инспектор и существующие диалоги документации/свойств. Общие для всех рисунков элемента |
| `junction` | Обязательные `name`, `documentation`, `properties` | Без изменения | Инспектор и существующие диалоги документации/свойств. Общие для всех рисунков junction |
| `relationship` | Обязательные `label`, `properties`; `documentation` запрещено | Добавить обязательное `documentation: string`; сохранить имя поля `label` | Подпись, свойства и документация общего отношения в инспекторе; отдельная линия лишь указывает на владельца |
| `view` | Обязательные `name`, `documentation`; `properties` запрещены | Добавить обязательное `properties: Record<string, string>` | Модель → Свойства представления. Документация и свойства конкретного вида |

`occurrence`, `connection`, anchors и их координаты не приобретают документацию
или свойства. Выбор рисунка лишь указывает на точного владельца данных:
`element`, `junction` либо `relationship` вместе с ID. Переименование, повторный
рисунок и переход в другой вид не копируют метаданные. У project/view свои ID;
они не должны маскироваться под модельный `ConceptRef`.

Пользовательское свойство с именем `documentation`, `Документация` или `name`
остаётся пользовательским свойством. Оно не становится встроенным полем.
`profileApplications` и атрибуты typed customization profiles также остаются
отдельным контрактом [CUSTOMIZATION.md](CUSTOMIZATION.md).

## Текст и уникальность свойств

- Документация, имена, подписи, ключи и значения — исходные строки. Пустая
  строка допустима; отсутствие обязательного поля, `null`, число и boolean
  ей не эквивалентны. Никакого trim, NFC/NFD преобразования, CRLF→LF,
  интерпретации HTML/Markdown либо числового приведения при хранении.
- Сохраняются ограничения v2: строка не более **8192 единиц UTF-16**,
  не более **64 свойств** у одного владельца, существующие бюджеты файлов и
  всего проекта. Escape-представление lone surrogate остаётся точным JSON;
  invalid UTF-8 транспорт не принимается. Лимиты raw multiplicity остаются
  отдельными и не увеличиваются.
- `properties` остаётся словарём **уникальных строковых ключей**. Уникальность
  сравнивается после JSON decoding, по точным единицам UTF-16, с учётом регистра.
  `owner` и `\u006fwner` — один ключ; `Owner`/`owner` и NFC/NFD написания — разные.
  Пустой ключ допустим в native-файле, пробелы сохраняются. Канонический порядок
  ключей — существующий UTF-16 порядок, включая ключи `"10"` и `"2"`.
- `__proto__`, `prototype` и `constructor`, accessors, скрытые свойства и
  значения вне JSON остаются запрещены. Строгий parser проверяет ключи до
  преобразования в обычный объект; нельзя сначала применять `JSON.parse`
  или `Object.fromEntries` к внешним данным и потерять повтор.
- Повторяющиеся свойства из внешнего формата не схлопываются в last-write-wins,
  даже если значения равны. Будущий импортёр должен обнаружить повтор до
  преобразования, показать владельца/ключ и отказать целиком. Пользователь
  может исправить источник; автоматические суффиксы или склейка значений не
  предусмотрены. Массив пар не является допустимым native `properties`.

Native v2 и v3 допускают пустой ключ. Диалог сохраняет такие ключи и исходный текст при неизменённом поле; создание/переименование
ключа требует непустого имени; пробельный ключ не создаётся неявно. Поиск может нормализовать свой поисковый
индекс, но не сохранённые значения и не владельца результата.

## Версии и политика миграции

| Данные на входе | Исторический reader v2 | Текущий reader v3 |
| --- | --- | --- |
| Корректный native v2 с metamodel `@2` | Читает без добавления полей; следующий Save пишет v2 | Читает через единственную чистую миграцию ниже |
| Native v1, чужой format/metamodel | Отказ `VERSION` | Отказ; общего legacy-конвертера это решение не вводит |
| Native v2 с полем, предназначенным только для v3 | Отказ `SCHEMA`, без попытки угадать версию | Отказ; сначала полная проверка исходного v2 |
| Корректный native v3 | Отказ `VERSION`, никакого удаления неизвестных полей | Строгая полная валидация v3 |
| Неизвестная версия выше поддерживаемой | Отказ `VERSION` | Отказ `VERSION` до подмены модели |
| Оболочка, отличная от `schemka-project-file@1` | Отказ `FILE_VERSION` | Отказ `FILE_VERSION`, пока её грамматика отдельно не изменена |

Единственная принятая миграция **v2 → v3** выполняется на полностью отделённом
кандидате после строгого parsing и полной проверки v2:

1. Скопировать все записи без изменения ID, имён, пользовательских ключей,
   значений, references, profiles/viewpoints и геометрии.
2. Добавить только `project.documentation = ""`, `project.properties = {}`,
   каждому relationship `documentation = ""`, каждому view `properties = {}`.
   Не брать значения из похожих пользовательских свойств.
3. Изменить только внутренний `project.formatVersion` с `2` на `3`.
4. Полностью проверить v3 и его канонические размеры. Добавленные пустые поля
   тоже расходуют бюджет: если файл/проект после миграции превышает лимит,
   отказать `LIMIT`, сохранив исходный вход. Ничего не обрезать.
5. Перед подменой повторно проверить revision/session ticket. Только затем
   принять целиком новый проект. Ошибка, отмена или устаревшая операция
   сохраняют текущую модель, обе истории, dirty baseline и файловую привязку.

Повторное чтение v3 не добавляет поля снова. Пустые новые поля обязательны;
запись не удаляет их ради уменьшения размера. Декодирование входа, миграция и
валидация — чистая подготовка, не команды с промежуточными событиями.

**Миграция не переписывает источник.** Редактор показывает факт
обновления формата, держит документ несохранённым до успешного Save As и
сохраняет v3 отдельным файлом или новым каталогом. Обычный Save не может
перезаписать привязанный v2 источник после миграции. In-place upgrade и
downgrade v3 → v2 запрещены этим решением; даже при пустых новых полях версия
не меняется обратно автоматически. Отдельный интерфейс миграции включается
только вместе с реализацией reader/validator/session и всеми её проверками.

## Один контракт во всех путях

Все перечисленные пути используют одну версионную границу `readProjectFiles` / `readProjectFile` и один pure converter `normalizeProject`; runtime-команды и `validateProject` принимают строгий v3; UI, Electron и
Git не получают собственных правил «исправления» данных.

| Путь | Инвариант |
| --- | --- |
| Import/native directory | Все записи и ссылки проверены до возврата кандидата; неизвестные поля и дубли не пропускаются |
| `.arkita` / прежний `.schemka.json` | Оболочка лишь переносит native-записи. Сериализация использует канонические значения core, а не поля формы |
| Native open/save/update | Открытие не пишет файлы. Перед записью данные проверены; отказ не меняет источник, текущий файл, каталог или journal. Низкоуровневый `atomicWrite` остаётся общим байтовым writer; schema boundary находится в `projectBytes`/file service |
| Git serialize/merge | Stable paths и whole-record merge сохраняются. Все три входа проверяются, даже при whole-side resolution. Конфликт документации/свойств одной записи требует выбора полной записи; не сливается по ключам молча |
| Git при v3 | Base/local/remote проходят один reader/converter в памяти перед сравнением. Для поддерживаемых v2 сторон добавляются те же пустые поля; несовместимая сторона отклоняет всё объединение. Только разрешённый и полностью проверенный итог может стать одной командой; удалённые ветки и исходные файлы при подготовке не переписываются |
| Undo/Redo | Правка метаданных и `applyProjectSnapshot` — атомарные команды. Exact values и IDs восстанавливаются вместе. Успешное открытие другого проекта очищает обе истории один раз; failed open их сохраняет |
| Project-session | Dirty сравнивает полные канонические байты, включая метаданные. Save ticket относится только к захваченным байтам; failed open не меняет token/baseline и не уничтожает pending save |

## Исторические проверки ADR и проверки реализации

Зафиксирован синтетический [metadata-v2.arkita](../schemka-model-core/fixtures/metadata-v2.arkita):
**4350 байт, 10 native records**, контракт базовой версии main
`51db57e44a380d9540805ae8a63259f7fb7acbd9`.
SHA-256: `94a7d4db59e6a34ba2d0b1160848163cf900fd07fff85f751f1c5efcdf7e2838`.
Fixture хранит реальные входные байты, а не создаётся через будущие defaults
`createProject` при запуске теста. Есть все пять владельцев, пустые имена,
подписи, документация и значения, пустой ключ, различимые NFC/NFD и case keys,
CRLF, Unicode, escaped lone surrogate, geometry и anchor.

[incompatibleMetadata](../schemka-model-core/fixtures/metadata-compatibility.js)
готовит из него несовместимые входы: старый v1, будущий v4, чужой metamodel,
unguarded additions в v2, отсутствующее поле, неверные типы, duplicate decoded
keys и внешние повторяющиеся строки свойств. Один и тот же набор проходит
через следующие проверки:

| Проверка | Файл |
| --- | --- |
| Frozen bytes, текущая схема, exact text, атомарные команды/load, обе истории, three-way merge всех сторон | [core](../schemka-model-core/test/metadata-contract.test.js) |
| Старый файл, каноническое переоткрытие, раздельные версии оболочки/модели, отказ до load | [IO](../schemka-model-io/test/metadata-contract.test.js) |
| Dirty baseline, token, pending save, rejected load, Undo/Redo и успешное повторное открытие | [session](../schemka-model-ui/test/metadata-contract.test.js) |
| Настоящие временные файлы/каталоги, native service с injected dialogs, bound save/update, отсутствие частичной записи | [native filesystem](../electron/test/metadata-contract.test.mjs) |

Проверки запускаются стандартным `npm test`. Реализация #40 сохраняет исходный v2 fixture, добавляет независимый ожидаемый `metadata-v3.arkita` и проверки strict-v2→v3, обязательных пустых полей, новых владельцев, обоих бюджетов миграции, отмены/устаревания и Save As с защитой пути и inode источника. Ранее зарезервированный v3 стал положительным случаем; неизвестная будущая версия в отрицательных тестах — v4.

## Последующие задачи и границы

Следующие issues редактирования метаданных project/relationship/view и их
поиска должны ссылаться на этот ADR как на принятое решение. Их критерии:
один v3 reader/converter, предсказуемое Save As после миграции, точный владелец,
сохранность исходного текста, уникальные ключи, атомарные Undo/Redo и все пути
сохранения/слияния выше. `A-EDITOR-093/094` и соответствующие карточки свойств
не считаются реализованными по факту принятия ADR; `A-EDITOR-126` остаётся
ссылкой на глобальный менеджер `A-ADV-020`, без удвоения объёма.

Вложенность, notes, per-occurrence styles/assets, Archi/XML import, отчёты и
глобальный менеджер свойств не входят в этот контракт. Финальная проверка
диалогов, сохранения/повторного открытия на Windows и release tag выполняются
локально после завершения текущей очереди в main. Node filesystem/injected
adapter проверки не заменяют native Windows GUI acceptance.
