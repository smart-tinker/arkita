# Версии Arkita

Arkita использует `MAJOR.MINOR.PATCH` с предварительным суффиксом
`-alpha.N`, `-beta.N` или `-rc.N` по [SemVer 2.0.0](https://semver.org/spec/v2.0.0.html).
До `1.0.0` проект находится в разработке: `0.7` — номер этапа, а не семь
стабильных поколений. Этот публичный репозиторий начинается с чистого исходного снимка: прежние теги
и бинарные файлы сюда не переносились.

## Как выбираем номер

| Изменение | Пример следующей версии | Правило Arkita |
| --- | --- | --- |
| Исправление ошибок и удобства существующих сценариев | `0.7.1-rc.1` | Увеличиваем PATCH; не меняем формат модели и договорённости совместимости. |
| Новый пользовательский сценарий или значительное расширение | `0.8.0-alpha.1` | Увеличиваем MINOR, PATCH обнуляем. |
| Несовместимое изменение до `1.0` | `0.8.0-alpha.1` | Отдельный MINOR, явное описание несовместимости и миграции. |
| Несовместимое изменение после `1.0` | `2.0.0-alpha.1` | Увеличиваем MAJOR, MINOR и PATCH обнуляем. |

Это договорённости проекта для периода `0.x`; SemVer сам не гарантирует
совместимость начальной разработки. Наш внешний контракт — документированные
операции с файлами `.arkita`, Git и CLI. `1.0.0` означает согласованный,
проверенный коллегами основной сценарий и принятые обязательства совместимости;
этот номер не назначается автоматически после некоторого количества сборок.

## Предварительные версии и приёмка

- `alpha.N` — состав и сценарии ещё меняются; `beta.N` — проверяем собранный
  набор функций; `rc.N` — состав выпуска зафиксирован, исправляем найденные ошибки.
- Счётчик RC начинается с 1 для каждой новой базовой версии. Новая функция
  за пределами согласованного состава переводится в следующий MINOR.
  Исторический `0.6.1-rc.1` сохраняется; текущая линия выпуска — `0.7.0`.
- Согласованный перенос Archi с диагностикой, прослеживаемостью и моделями
  ≥5000 записей — новый состав **`0.7.0-rc.1`**, следующий MINOR. Его RC-состав
  зафиксирован шестью критериями; это не дополнительный набор функций для
  `0.6.1-rc.2`. Старые версии и Latest сохраняются.
- Исправление навигации и папок после проверки импорта — **`0.7.0-rc.2`**.
  Оно остаётся в согласованном сценарии работы с перенесённой моделью; native
  формат, ID и семантические типы не меняются. Это не стабильный выпуск.
- Исправления ревью проекта после RC2 выпущены как **`0.7.0-rc.3`**:
  многоконный Git/Cut, асинхронное открытие, вложенное выравнивание и
  диагностика XML-экспорта.
- **`0.7.0-rc.4`** опубликован: открытие файла без лишнего пустого окна и
  выбор фона представления по теме приложения.
- В **`0.7.0-rc.5`** добавлены безопасное удаление доказанных дубликатов в
  журналах новых успешных сохранений файлов и native-каталогов и постраничный
  список изменений Git для больших моделей. Существующие, прерванные и
  неоднозначные журналы сохраняются. Формат модели и зависимости не меняются.
- Стабильная **`0.7.0`**
  опубликована 29 октября 2026 года после приёмки Эльдара. Отличия от
  функционального RC5 — версия, документы и исправление исчезающих подписей
  на Windows при дробном масштабе SVG. Состав, целевые проверки Windows и
  оставшиеся ограничения указаны в описании выпуска; это не полная регрессия.
- Порядок: `0.7.0-rc.4 < 0.7.0-rc.5 < 0.7.0`.
  Новый RC публикуется под новым номером; уже выданные файлы не заменяем.
- RC не становится финальным выпуском по факту сборки или автотестов.
  Нужны проверки финального коммита, установка и GUI на Windows для точного
  пакета, проверка сохранения пользовательских данных, затем явная приёмка Эльдара.
  Оставшиеся ограничения перечисляются в описании пакета.
- После приёмки выпускаем **`0.7.0`** без суффикса и без новых функциональных
  правок. Смена версии требует нового пакета; проверяем его версию, состав,
  чистую установку и обновление RC4 с сохранением настроек и моделей отдельно.
  Номер `1.0.0` остаётся отдельным решением после тестирования коллегами.

На GitHub RC создаётся как **Pre-release**: `prerelease: true`,
`make_latest: "false"`. Он не заменяет текущий Latest. Поля и правила описаны в
[GitHub Releases API](https://docs.github.com/en/rest/releases/releases#create-a-release).
Тег совпадает с версией `package.json` с префиксом `v`, например
`v0.7.0`; описание, имена дистрибутивов и SHA-256 относятся к одному
проверенному коммиту. До публикации готовность обозначается отдельно, а не
наличием планируемой ссылки на тег.

## Версия приложения, пакета и модели

Единственный источник версии приложения — корневой `package.json`; корневые
поля `package-lock.json` должны совпадать с ним. Electron передаёт эту версию
в «Справка → Об Arkita» через `app.getVersion()`; суффикс RC не отбрасывается.
Имя установщика включает полную версию:
`Arkita-0.7.0-win-x64-setup.exe`.

Версия приложения независима от `.arkita` envelope `schemka-project-file@1`,
native writer `schemka-project@4`, метамодели `schemka-archimate4@2` и нотации
ArchiMate 4. Переход на новый RC сам по себе не мигрирует модель и не подтверждает
нормативное соответствие нотации. Текущий CLI сообщает `sourceVersion` входной
модели; это версия формата, а не версия Arkita.

[Electron-builder](https://www.electron.build/v26/docs/configuration/)
поддерживает полную SemVer-строку приложения, но числовая Windows/NSIS-версия
состоит из четырёх чисел. В закреплённом builder `26.15.3` без `buildNumber`
`0.7.0-rc.5` преобразуется в `0.7.0.0`: этот числовой ресурс сам по себе не
различает RC и финальный выпуск. Полную версию проверяем в «Об Arkita»,
пакетном `package.json` и имени файла; `buildVersion`/`buildNumber` не подменяют
версию приложения. Сборки пока не подписаны сертификатом издателя.
