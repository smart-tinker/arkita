# Windows acceptance: поиск, редактирование группы и SVG

План локальной приёмки поиска и «Где используется» #20 (historical issue #20) / #21 (historical issue #21) вместе со всей текущей очередью [#23–27](ROADMAP.md): выбор и перенос группы, выравнивание, reuse/clone фрагмента, контракт метаданных и самостоятельный SVG. **Локальный Codex подключается после слияния всех изменений проверяемого набора в `main` и автоматических проверок итогового `main`.** Здесь описан план, результаты Windows ещё не выставлены. Нужны настоящая Windows x64, проверяемый дистрибутив и наблюдение его native GUI. Node/DOM-тесты дополняют эту проверку.

Исходные N1–N6, K1–K5, S1–S2 и V1–V2 остаются обязательными. Новые группы G/A/C/M/E перечислены ниже. #26 принят как контракт совместимости: текущий native v2 сохраняется, будущий v3 и новый metadata UI не реализованы. Поэтому проверяются старые данные и отказ несовместимых входов, а не несуществующий экран миграции.

## 1. Зафиксировать исходники и сборку

Взять **полный 40-символьный SHA итогового `main` из отчёта о завершённом слиянии**. В нём должны находиться корпус, поиск, «Где используется», все изменения #23–27, их app-интеграция и исправления ревью. Сверить с итоговой таблицей [ROADMAP](ROADMAP.md) и успешным общим прогоном для этого SHA. SHA незамёрженной ветки не является точкой передачи локальному Codex. `FINAL_COMMIT_SHA` ниже — заменяемое значение, а не уже проверенный коммит. Проверять зафиксированный SHA, даже если `main` позднее сдвинулся.

Из локального клона Arkita, в PowerShell, создать отдельный checkout. Если каталог уже существует, выбрать другое свободное имя; текущую работу не сбрасывать.

```powershell
$FINAL_COMMIT_SHA = "FINAL_COMMIT_SHA"
if ($FINAL_COMMIT_SHA -notmatch '^[0-9a-fA-F]{40}$') { throw "Укажите полный SHA main из отчёта о слиянии" }
git fetch origin main
if ($LASTEXITCODE -ne 0) { throw "Не удалось получить main" }
git merge-base --is-ancestor $FINAL_COMMIT_SHA origin/main
if ($LASTEXITCODE -ne 0) { throw "Проверяемый коммит не найден в main" }
git worktree add --detach ..\arkita-windows-acceptance $FINAL_COMMIT_SHA
if ($LASTEXITCODE -ne 0) { throw "Checkout не создан" }
Set-Location ..\arkita-windows-acceptance
$ArkitaActualCommit = (git rev-parse HEAD).Trim()
if ($ArkitaActualCommit -ne $FINAL_COMMIT_SHA) { throw "HEAD не совпадает с заданным SHA" }
git status --short
node --version
npm --version
```

Зафиксировать Windows build, CPU/RAM, Node/npm, SHA и чистоту checkout. Для сборки использовать Node 22.12+ согласно [инструкции Windows](../WINDOWS.md); точные зависимости задаёт lockfile. Выполнять следующие команды **по очереди**, сохранять полный вывод и код завершения, продолжать только после `0`:

```powershell
npm ci --ignore-scripts
npm run build
npm test
npm run check
npm run package:win
```

Это существующие команды из [package.json](../../package.json). `npm test` сам повторяет build и включает модельные, DOM, IO, platform и Electron boundary tests через [общий runner](../../scripts/test.mjs). Для итоговой проверки `SCHEMKA_NOTATION_SOURCE_ONLY` не должен быть установлен в `1`: app-тесты должны проверять собранные production-файлы. Записать реальные test/pass/fail/skip и убедиться, что нужные suites исполнились; одной строки об успешном запуске runner недостаточно.

`package:win` подготавливает встроенный Git и создаёт NSIS x64 с `--publish never`. Первой сборке нужны официальные загрузки Electron/NSIS/MinGit. Если для диагностики нужен запуск из исходников, после `npm ci --ignore-scripts` выполнить `node node_modules/electron/install.js`, затем `npm run desktop`; этот запуск не заменяет приёмку упакованного приложения.

```powershell
$ArkitaVersion = (node -p "require('./package.json').version").Trim()
$ArkitaInstaller = "release/windows/Arkita-$ArkitaVersion-win-x64-setup.exe"
Get-FileHash -Algorithm SHA256 $ArkitaInstaller
```

Закрыть ранее запущенные копии Arkita, установить именно полученный файл и запустить установленное приложение. Зафиксировать путь запуска и версию в «Об Arkita». Версии недостаточно для идентификации: в отчёт входит SHA-256 установщика. Если к выпуску выбран portable, использовать существующий рецепт [«Сборка portable EXE»](../WINDOWS.md#сборка-portable-exe), зафиксировать его отдельный SHA-256 и проверить именно portable. PASS другого формата на него не переносится.

## 2. Подготовить модель для GUI

Существующий [where-used-fixture.js](../../schemka-model-ui/test/where-used-fixture.js) создаёт модель с одинаковыми названиями концептов и видов, повторными рисунками, далёкими координатами и viewpoint. [Тесты диалога](../../schemka-model-ui/test/where-used-ui.test.js) и [app-тесты](../../schemka-model-ui/test/where-used-app.test.js) используют этот fixture; их выполнение само по себе не открывает Windows GUI. Для отдельного лога этой итерации после build можно выполнить:

```powershell
node --test --test-concurrency=2 --test-reporter=tap schemka-model-ui/test/model-search.test.js schemka-model-ui/test/model-search-app.test.js schemka-model-ui/test/concept-usages.test.js schemka-model-ui/test/where-used-ui.test.js schemka-model-ui/test/where-used-app.test.js
```

Экспортировать fixture штатным сериализатором в новый временный каталог вне checkout. Скрипт ниже создаёт исходную модель, перечень точных ID и вариант для проверки 220 результатов. Он не меняет код приложения и не перезаписывает существующие файлы.

```powershell
$ArkitaAcceptanceDir = Join-Path $env:TEMP ("Arkita acceptance " + (Get-Date -Format "yyyyMMdd-HHmmss"))
@'
import { mkdirSync, writeFileSync } from "node:fs";
import { join } from "node:path";
import { usageFixture } from "./schemka-model-ui/test/where-used-fixture.js";
import { fixtureId } from "./schemka-model-core/fixtures/relationship-project.js";
import { serializeProjectFile } from "./schemka-model-io/src/index.js";
const dir = process.argv[2];
mkdirSync(dir);
const { state, ...ids } = usageFixture();
writeFileSync(join(dir, "navigation.arkita"), serializeProjectFile(state), { flag: "wx" });
writeFileSync(join(dir, "navigation-ids.json"), JSON.stringify(ids, null, 2), { flag: "wx" });
const large = structuredClone(state);
for (let n = 1000; n < 1220; n++) large.elements.push({
  ...structuredClone(state.elements[0]), id: fixtureId("el", n), name: `Acceptance bulk ${n}`
});
writeFileSync(join(dir, "search-220.arkita"), serializeProjectFile(large), { flag: "wx" });
'@ | node --input-type=module - "$ArkitaAcceptanceDir"
if ($LASTEXITCODE -ne 0) { throw "Не удалось подготовить fixture" }
Get-FileHash -Algorithm SHA256 "$ArkitaAcceptanceDir\navigation.arkita"
```

Открыть `navigation.arkita` через **Файл → Открыть…**, подтвердить замену учебного примера. Двойной щелчок по `.arkita` в Проводнике не является поддерживаемым способом открытия. Хранить исходный fixture неизменным; результаты GUI сохранять через «Сохранить как…» под другими именами. При повторной генерации новые рисунки получают новые ID, поэтому использовать `navigation-ids.json` именно своего запуска.

| Что искать по полному ID из `navigation-ids.json` | Ожидаемые использования |
|---|---|
| `refs.element` | 4 рисунка в 2 видах: 2 скрыты viewpoint первого вида, 2 видимы во втором. |
| `refs.junction` | 2 рисунка в 2 видах, оба видимы. |
| `refs.relationship` | 4 соединения в 2 видах: 2 скрыты в первом, 2 видимы во втором. |
| `refs.unused` | Общий элемент существует, рисунков нет. |

`primaryViewId` — вид с viewpoint `Application information`; `otherViewId` — второй вид без этой привязки. Их названия одинаковы. Для точного перехода сравнивать ID вида и рисунка; `visibleOccurrences`, `visibleConnections`, `visibleJunctionId` перечислены в manifest. Строки `<img …>`, `<svg …>`, `<script>` в именах — намеренные текстовые данные fixture, они должны отображаться буквально.

### 2.1. Модели для выбора, копирования, метаданных и SVG

После создания `$ArkitaAcceptanceDir` выполнить следующий скрипт из того же checkout. Он использует [SVG fixture](../../schemka-model-ui/fixtures/svg-export-project.js), добавляет второй рисунок концепта A для групповых операций и сохраняет [замороженный metadata v2](../../schemka-model-core/fixtures/metadata-v2.arkita) вместе с [преднамеренно несовместимыми вариантами](../../schemka-model-core/fixtures/metadata-compatibility.js). Все файлы синтетические; `wx` предотвращает перезапись предыдущих результатов.

```powershell
@'
import { writeFileSync } from "node:fs";
import { join } from "node:path";
import { createStore } from "./schemka-model-core/src/index.js";
import { serializeProjectFile } from "./schemka-model-io/src/index.js";
import { svgExportProject } from "./schemka-model-ui/fixtures/svg-export-project.js";
import { metadataFixture, metadataEnvelope, incompatibleMetadata } from "./schemka-model-core/fixtures/metadata-compatibility.js";
const dir = process.argv[2];
const write = (name, bytes) => writeFileSync(join(dir, name), bytes, { flag: "wx" });
const source = svgExportProject(), primaryViewId = source.state.views[0].view.id;
const svgBytes = serializeProjectFile(source.state);
write("svg-source.arkita", svgBytes);
write("native-model.svg", svgBytes);
const editing = createStore(source.state);
const duplicateA = editing.execute({ type: "addOccurrence", viewId: primaryViewId,
  concept: { kind: "element", id: source.ids.A }, bounds: { x: -430, y: 40, width: 140, height: 60 }
}, editing.revision).created.occurrenceId;
const editingState = editing.snapshot;
write("editing.arkita", serializeProjectFile(editingState));
write("editing-ids.json", JSON.stringify({ primaryViewId, otherViewId: source.state.views[1].view.id,
  concepts: source.ids, drawings: { ...source.draws, A2: duplicateA }, anchors: source.anchors }, null, 2));
const overflow = structuredClone(editingState), view = overflow.views.find(item => item.view.id === primaryViewId);
Object.assign(view.occurrences.find(item => item.id === source.draws.A).bounds, { x: 1000000, width: 1000000 });
view.occurrences.find(item => item.id === source.draws.B).bounds.width = .1;
write("alignment-overflow.arkita", serializeProjectFile(overflow));
write("metadata-v2.arkita", metadataFixture().bytes);
const invalid = incompatibleMetadata().map(({ name, files, code }, index) => {
  const file = `metadata-invalid-${index + 1}.arkita`;
  write(file, metadataEnvelope(files)); return { file, name, expectedCode: code };
});
write("metadata-invalid.json", JSON.stringify(invalid, null, 2));
'@ | node --input-type=module - "$ArkitaAcceptanceDir"
if ($LASTEXITCODE -ne 0) { throw "Не удалось подготовить fixtures очереди" }
Get-FileHash -Algorithm SHA256 "$ArkitaAcceptanceDir\editing.arkita", "$ArkitaAcceptanceDir\svg-source.arkita", "$ArkitaAcceptanceDir\metadata-v2.arkita"
```

`editing-ids.json` задаёт точные концепты, рисунки и anchor. A/A2 — два рисунка одного ApplicationComponent, B — Service, D — Device, J/K — And/Or junctions. Главный вид содержит шесть видимых экземпляров и пять соединений. Flow R связывает A с B и содержит именованный anchor; T соединяет R с J; U — самосвязь B. Goal H и его связь Q скрыты viewpoint. Второй вид содержит отдельный рисунок H. Для SVG использовать исходный `svg-source.arkita` с пятью видимыми экземплярами, чтобы не смешивать его ожидаемый состав с результатами копирования.

В fixture намеренно оставлен импортированный ReadWriteAccess S между A и D, запрещённый текущим правилом создания. Его существование допустимо для чтения, диагностики и reuse. Clone группы A/A2/B/J проходит обычную границу создания; clone всей группы, включающей S, должен целиком отклониться. Это отдельный контроль C6, а не обещание разрешить новую запрещённую связь.

Все имена и ID сверять по manifest своего запуска. Нельзя принимать одни только одинаковые подписи за доказательство reuse либо независимости концептов. Перед каждым блоком открывать исходник заново; результаты сохранять под новыми именами, сохраняя исходники и их SHA-256.

Обязательный `npm test` уже включает новые core/IO/session/native и app-сценарии. Повторять весь unit-набор для каждой GUI-строки не требуется. В его логе отдельно отметить metadata-contract и [native export guard](../../electron/test/export-native-guard.test.mjs), а Windows-specific skips проверить по причинам. Недоступный 8.3 alias или непройденный native GUI не превращается в PASS по Linux-логу. Дополнительные focused-прогоны нужны при конкретном дефекте или незавершённом сценарии.

## 4. Клавиатура, незавершённые действия и native окна

Для K1 предварительно снова открыть исходный `navigation.arkita`. Для K2–K5 использовать рабочую копию и фиксировать состояние до действия.

| ID | Действия | Ожидаемое поведение |
|---|---|---|
| K1 | На втором виде выбрать рисунок A. В поиске найти другой концепт B, передать фокус результату через Enter/ArrowDown из поля, нажать `Delete`, затем `F2`. Нажать `Escape` на результате и отдельно в непустом поле поиска. | Delete/F2 не удаляют и не переименовывают прежний A; не появляется ошибочный диалог. Escape очищает поиск и возвращает фокус в поле, не снимая прежнее выделение на полотне. В поле Delete редактирует текст обычным образом. |
| K2 | Оставить результаты поиска, начать inline-переименование и ввести черновик без Enter. Попробовать щёлкнуть поиск/результат и вызвать Ctrl+F. Отдельно начать переименование в свойствах и попробовать «Где используется…». Повторить блокировку перехода при открытом редакторе документации/свойств. | Поиск/переход не должен незаметно подтвердить или уничтожить черновик. Текущую правку можно явно завершить или отменить и после этого продолжить. Проверять настоящий pointerdown → click и клавиатурную активацию, а не только программный `.click()`. Неудачное поведение записать как дефект с шагами. |
| K3 | Открыть список использований, закрыть Escape, снова открыть для другого концепта; быстро дважды активировать одну строку. Закрыть список/свойства, переключить вид и открыть список заново. | Escape/Close восстанавливают полезный фокус; новый список относится к новому концепту и виду. Повторная активация не создаёт повторного перехода или мутации. Модальный диалог не пропускает клики/клавиши к скрытым за ним destructive-действиям. |
| K4 | При несохранённых изменениях и доступном Redo вызвать Файл → Открыть. Отменить системный выбор файла. Затем выбрать другой fixture, но отменить «Заменить модель этим файлом» кнопкой «Отменить выбор». Повторить поиск и использования. | Обе отмены сохраняют прежнюю модель, dirty, историю и рабочую файловую привязку. После отмены поиск снова доступен. Ни отложенная загрузка, ни прежняя строка поиска не должны открыть другой объект или заменить модель. При успешном подтверждённом открытии другого fixture поиск очищается, история загрузки начинает новую сессию. |
| K5 | Отменить native «Сохранить как…». Закрыть окно приложения с несохранённой моделью/черновиком и выбрать отмену выхода. | Отмена сохранения не помечает изменения сохранёнными. Отмена выхода оставляет окно и данные доступными; после завершения/отмены правки поиск и использования работают. |

Внутренние **stale**-случаи — старый store/revision, смена selection/view и вызов уже удалённой кнопки — воспроизводятся в [where-used-ui.test.js](../../schemka-model-ui/test/where-used-ui.test.js), [where-used-app.test.js](../../schemka-model-ui/test/where-used-app.test.js) и [model-search.test.js](../../schemka-model-ui/test/model-search.test.js). Нельзя честно воспроизвести их все обычными кликами через модальный native GUI. Сохранить лог этих тестов отдельно от ручных K3–K4; если конкретный native race не удалось воспроизвести, отметить это, а не выставлять ему PASS. Старый список после смены модели должен закрыться либо отказать в переходе с объяснением, не применяя устаревшее действие.

## 5. Сохранность, фокус и оформление

**S1 — байты после навигации.** Снова открыть `navigation.arkita`, выполнить N1–N5 без правок, сохранить как `navigation-after.arkita` в каталог acceptance. Сравнить размер и SHA-256 с исходником: они должны совпасть. Закрыть Arkita, открыть сохранённый файл через меню после нового запуска и повторить N3–N5. Числа, ID, документация/свойства и viewpoint сохраняются.

```powershell
Get-Item "$ArkitaAcceptanceDir\navigation.arkita", "$ArkitaAcceptanceDir\navigation-after.arkita" | Select-Object Name, Length
Get-FileHash -Algorithm SHA256 "$ArkitaAcceptanceDir\navigation.arkita", "$ArkitaAcceptanceDir\navigation-after.arkita"
```

**S2 — обе ветки истории.** На исходном fixture переименовать модель в `Past`, затем в `Future`, выполнить Undo. Должны остаться имя `Past`, несохранённые изменения и доступные Undo и Redo. Выполнить поиск → свойства → использования и отмену открытия из K4: имя, dirty и доступность истории не меняются. Сохранить как `past.arkita`, сделать Redo до `Future`, Undo до `Past`, сохранить как `past-again.arkita`. Файлы `past.arkita` и `past-again.arkita` должны совпасть по размеру и SHA-256. Сохранение вправе очистить dirty; поиск и навигация — нет. История не обязана сохраняться между перезапусками приложения.

**V1 — native фокус и доступность.** Пройти N2–N5 клавишами Tab/Shift+Tab/Enter/Escape. Фокус виден; заголовок диалога, ID, причина скрытия и пустое состояние доступны для чтения. Tab не уходит за модальный диалог. Если используется Narrator, отдельно записать фактически проверенные объявления названия диалога, числа результатов и ошибки; DOM aria-атрибуты не являются отчётом о screen reader acceptance.

**V2 — окно, DPI и темы.** Повторить цепочку N2–N4 в обычном окне и узком окне около 800 × 600, при масштабе Windows 100% и 150% (200% — если доступен), в светлой, тёмной и системной темах. У приложения есть минимальный размер окна; не требовать мобильного размера, который Electron не позволяет. Поиск доступен через панель «Модель»/Ctrl+F, список и диалог прокручиваются, длинные ID/имена читаются, кнопки закрытия достижимы, выделение/фокус не сливаются с фоном. Записать размеры, DPI, тему и снимки проблемных состояний. Не превращать непроверенную комбинацию в PASS.

Для Save As дополнительно использовать каталог и имя с кириллицей и пробелами, например `Проверка Arkita\Модель после навигации.arkita`, и открыть результат после перезапуска. Более широкий native smoke сохранения/установки описан в [WINDOWS.md](../WINDOWS.md); он остаётся отдельной частью приёмки выпуска.

## 11. Отчёт и релизный тег

К отчёту о слиянии / связанному PR приложить фактический отчёт Windows-приёмки:

- точный SHA, состояние checkout, версию из этого `package.json`, Windows build/машину, Node/npm;
- команды, exit codes, полные логи и фактические test/pass/fail/skip;
- тип, имя и SHA-256 проверенного дистрибутива, путь запуска, SHA-256 fixture;
- N1–N6, K1–K5, S1–S2, V1–V2, G1–G5, A1–A4, C1–C6, M1–M3, E1–E6: `PASS`, `FAIL`, `BLOCKED` или `NOT RUN`, доказательство/шаги; до исполнения все пункты считаются `NOT RUN`;
- найденные дефекты с P0–P3, влиянием, воспроизведением, ожидаемым/фактическим результатом; ограничения и непроверенные комбинации явно отдельно.

**Тег создаётся отдельным действием локального Codex после отчёта и принятия результата владельцем.** В текущей базе package version — `0.5.1`; она не задаёт автоматически версию следующего выпуска. До тега согласовать новую версию, синхронизировать package/lockfile и release notes, убедиться, что целевой коммит входит в `main`. Уже опубликованный тег не переносить на другой коммит. Если исходники, версия или пакет изменились после acceptance, обновить сборку, хэш и относящиеся к изменению проверки; нельзя приписывать новому артефакту результаты старого. Метка stable следует из принятого отчёта по конкретному дистрибутиву, а не из успешного завершения `npm test`.
