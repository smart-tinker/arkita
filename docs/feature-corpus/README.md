# Корпус функций Arkita по документации Archi

**Назначение:** превратить документированные возможности Archi в проверяемые требования к Arkita — Windows desktop редактору **ArchiMate 4**. Это рабочая программа развития с небольшими issues и PR, а не обещание реализовать весь Archi одним изменением или подтверждение соответствия стандарту.

## Зафиксированный срез

Основной источник — [Archi User Guide 5.10.0](https://www.archimatetool.com/downloads/archi/Archi%20User%20Guide.pdf), полученный 18 октября 2026 года. PDF: 176 страниц, 5 307 717 байт, SHA-256 `1c80af5ac31b1bd2057b2494907c9071cfcec12a1e141773b5fadf6f015f2731`. Печатная страница `n` соответствует странице PDF `n + 1` из-за обложки. Ссылки на официальный URL могут со временем получить другую версию; при следующем обновлении корпуса сравнивать версию и хэш, сохранять ID существующих карточек.

База Arkita — `main`, `d075e67c7ca6e7720f537102e245a59f53808b32` (historical commit), package version 0.5.1, дерево `aa73565ad3a960d2876b26cedc4e6a1f5c943c6a`. Все 316 файлов исходного снимка сверены с Git blob SHA. Код унаследованного Mermaid-приложения в корневом `src/` и его сайта не считается функциональностью Arkita. Поставляемые модули определены в `package.json` → `build.files`.

Состав корпуса: **127 карточек редактора, 173 карточки расширенных возможностей и 39 дополнений/уточнений — всего 339 записей**. Карта охватывает все **184 строки оглавления Guide**. ## Текущий набор разработки

**19 октября 2026 владелец подтвердил завершение всего применимого корпуса до передачи локальному Codex.** Общая программа — #39 (historical issue #39), направления и зависимости — [PROGRAM.md](PROGRAM.md), соответствие всех исходных записей задачам — [program.json](program.json). Исходные карточки и историческая оценка сохраняются. Завершение первой итерации не является границей новой программы.

## Как читать карточки

Карточка содержит стабильный ID, задачу пользователя, документ/раздел/страницу, предполагаемое поведение Arkita, зависимость от нотации и критерии приёмки. Критерии — самостоятельные продуктовые требования Arkita; источник не гарантирует, что Archi реализует каждую нашу проверку таким же способом.

- **Independent** — механика редактора; используем существующий каталог Arkita.
- **Adapt** — поведение зависит от типов, отношений, вложенности, представлений или профилей; правила ArchiMate 4 проверяются по [источникам нотации Arkita](../NOTATION-SOURCES.md). Матрица ArchiMate 3.2 не переносится.
- **Exclude** — специфическая технология/поставка Archi либо отсутствие отдельной переносимой функции. Причина сохраняется, чтобы пропуск был проверяемым.

В дополнениях используются эквивалентные G/A и C; **C** обозначает совместимость с внешним форматом. Импорт требует собственного контракта преобразования и отчёта о потерях. Canvas, Sketch, scripting и плагины учитываются как отдельные направления общей программы с собственными границами и критериями.

`coverage.json` различает `implemented-in-code`, `partial`, `absent`, `unverified` и `excluded`. Даже `implemented-in-code` означает только наличие механизма в проверенном коде. Исполнение тестов, приёмка критериев, доступность в поставляемом UI и Windows GUI имеют собственные доказательства. Имя файла или похожий тест не закрывает всю карточку. Неизвестное состояние не превращается ни в «отсутствует», ни в «реализовано».

Это распределение записей выбранного корпуса, а не оценка качества Arkita и не процент готовности релиза. Например, Git, история, профили и viewpoint уже составляют существенную работающую базу, хотя большие будущие карточки остаются частичными.

Статусы базы сохраняются историческими. Результаты текущей очереди и ссылки на PR фиксируются в ROADMAP. Обновление baseline — отдельный полный пересмотр; настоящее изменение документации не меняет 339 записей `coverage.json`, исходные карточки, карту разделов или статистику выше. Один небольшой issue может закрывать полезную часть нескольких больших карточек, оставляя остальные критерии открытыми.

## Границы архитектуры

Перед реализацией переиспользовать store-команды, историю, typed concept references, существующие profiles/viewpoints, project-session и встроенный Git. Навигация, поиск, камера и предварительный просмотр не являются мутациями модели. Изменение концепта действует во всех его рисунках; изменение occurrence/connection относится к конкретному виду.

База новой программы `eb643c46` имеет ограничения: `parentOccurrenceId` должен быть `null`; нет отдельных records заметок/визуальных групп; нет per-occurrence styles/assets; у модели и отношения нет поля документации, у вида оно уже есть; пользовательские свойства — словарь с уникальными ключами. Решение для метаданных принято в [ADR #26](../METADATA-CONTRACT.md): замороженный v2, отдельный v3 и явная миграция с сохранением исходной копии. Миграция реализуется в #40. Для notes/assets/вложенности нужны собственные контракты в #49/#50. Нельзя молча добавлять неподдерживаемые поля, терять неизвестные данные или имитировать новый тип визуальным названием существующего элемента.

Существующие ограничения сохранения и отдельная нормативная неопределённость сохраняются в [readiness](../RELEASE-1.0-READINESS.md). Этот документ не заменяет их тесты и не блокирует вновь согласованную работу.

## Цикл работы и готовность

`Карточка → issue конкретного пробела → критерии/фикстура → отдельный PR → focused tests → независимое review → проверки перед слиянием → merge в main → общий runner на итоговом main → Windows acceptance → release tag`.

Для новых функций порядок R1/R2/… отделён от тяжести **подтверждённых ошибок**: P0 — массовая/необратимая потеря данных либо полный отказ; P1 — сломан основной сценарий или реальная угроза данным; P2 — существенная проблема с рабочим обходом; P3 — локальная косметика или небольшая шероховатость. Номер очереди не утверждает тяжесть отсутствующей функции.

Полнота извлечения проверяется покрытием всех разделов зафиксированного Guide и выбранного реестра дополнительных источников. Это не означает полноту реализации, инвентаризацию всей экосистемы плагинов или нормативную сертификацию.

## Разделение работы

Здесь выполняются исследование, корпус, GitHub issues/ветки/PR, реализация, code review, тесты модели/команд/IO/Git/DOM и доступного renderer, исправления, слияние в `main` и подготовка выпуска. **Локальный Codex подключается, когда все изменения проверяемого набора уже в `main` и итоговый `main` прошёл автоматические проверки.** Он получает точный SHA этого `main` и сценарий для реальной Windows машины, проверяет соответствующий дистрибутив и проставляет релизный тег по поручению владельца.

Изменения Electron, native files, packaged Git, clipboard, DPI и печати сопровождаются короткими Windows smoke-сценариями соответствующей итерации; окончательная приёмка остаётся финальным этапом. Зелёные Linux/DOM-тесты не помечают Windows-пункты как выполненные.
