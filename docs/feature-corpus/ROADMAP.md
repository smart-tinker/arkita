# Очередь реализации

Корпус — инвентаризация требований; в GitHub выносятся небольшие проверяемые пробелы. Исходная база: `d075e67c7ca6e7720f537102e245a59f53808b32` (0.5.1). Историческое покрытие этой базы хранится в [coverage.json](coverage.json). Таблица ниже показывает последующую работу и не переписывает историю задним числом.

R1/R2/R3/R4 обозначают порядок и зависимости разработки. Это не сроки, версии релизов и не тяжесть дефектов P0–P3. Независимый SVG-экспорт может идти параллельно копированию; задачи с изменением формата начинаются с принятого контракта совместимости.

Эта таблица сохраняет порядок первой итерации #20–22, а не задаёт базы новых PR. Текущие #23–27 проверяются и сливаются отдельными изменениями по зависимостям из таблицы выше. Ссылки, полный head/merge SHA, результаты и ограничения публикуются в соответствующих PR. Промежуточные focused-счётчики не складываются и не подменяют итоговый aggregate.

Передача локальному Codex начинается после слияния **всего текущего набора**, включая финальную app-интеграцию и документацию. Она относится к точному итоговому `main`, а не к ранее принятому поиску, отдельной ветке или одному из промежуточных PR.

При слиянии двигаться снизу вверх, каждый раз проверять актуальные base/head и diff. После изменения итогового дерева повторить затронутые проверки и общий runner на финальном коммите. Дистрибутив и релизный тег относятся к тому же проверенному исходному состоянию. Автоматического повышения версии или публикации релиза эти PR не выполняют.

## Текущие направления и зависимости

Метаданные, папки, visual records, ресурсы и ordered properties используют
[единый Native V4](../NATIVE-V4.md). На этом контракте работают поиск и массовые
свойства, оформление/вложенность, clipboard, templates/Canvas, отчёты и IO.
Окна моделей имеют независимые store/session/Undo и guarded native boundaries;
Git продолжает использовать общий codec и не переписывает старые commits при
миграции. Автоматизация использует закрытый JSON manifest и команды store,
без исполнения JavaScript из модели.

Все направления #40–58 описаны в [PROGRAM.md](PROGRAM.md) и
[реестре реализации 0.6.0](RELEASE-0.6.0.md). Таблица выше сохраняет итог
первой итерации: ограничения её PR не являются текущей картой возможностей.
В новом реестре отдельно указаны ограниченные адаптеры импорта, геометрическая
и семантическая вложенность, отсутствие периодического autosave и ограничения
native/Git. Подтверждение каждого применимого исходного критерия остаётся
отдельным от family-level наличия кода.

## Проверки и Windows-приёмка

Focused tests и независимое review проверяют конкретные изменения; их счётчики
не складываются. Финальные `npm test` и `npm run check` относятся к точному
итоговому исходному дереву. После него сборка и Windows-протокол фиксируют
тот же source SHA и SHA-256 дистрибутива. Исправление после проверки требует
повторить затронутые проверки и финальный gate.

[WINDOWS-ACCEPTANCE.md](WINDOWS-ACCEPTANCE.md) сохраняет сценарии предыдущей
итерации; дополнения 0.6.0 перечислены в [Windows guide](../WINDOWS.md#новые-сценарии-приёмки-060)
и [release ledger](RELEASE-0.6.0.md#windows). Реальные native dialogs, clipboard,
ассоциации, шрифты, печать, DPI, второй монитор и авторизация не превращаются
в PASS из Linux/DOM результата. Невыполненный случай остаётся pending/unrun;
отсутствующая реализация фиксируется отдельно как пробел source.

Публикация и финальное закрытие критериев оформляются после соответствующих
проверок. Исторический [readiness](../RELEASE-1.0-READINESS.md) сохраняется;
новая версия и новое доказательство не стирают прежние ограничения.
