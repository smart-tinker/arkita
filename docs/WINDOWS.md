# Arkita для Windows

Публичный исходный снимок соответствует версии 0.7.0. Ранее собранные
установщик, portable EXE и release assets сюда не перенесены; сейчас этот
репозиторий не публикует бинарные сборки. Проверенные будущие downloads будут
появляться на [странице выпусков](https://github.com/smart-tinker/arkita/releases).

Целевой формат поставки — Windows x64 NSIS-установщик для текущего пользователя,
с ярлыком в меню «Пуск» и ассоциацией `.arkita`. Portable EXE — дополнительный
вариант, который проверяется отдельно. Эта страница описывает сборку, состав и
приёмку; наличие исходников или успешного CI само по себе не подтверждает GUI
приёмку конкретного установщика.
[README](../README.md#версия-и-распространение) описывает текущее состояние
публичных сборок. [Правила версий](VERSIONING.md) определяют статус RC и переход
к будущему выпуску. [Реестр реализации 0.6.0](feature-corpus/RELEASE-0.6.0.md)
описывает историческую базовую функциональность.

Начиная с `0.5.0-alpha.1`, Windows-дистрибутив включает официальный MinGit 2.56.0.2 x64
для [совместной работы через Git](GIT.md). `npm run package:win` сначала
проверяет закреплённый SHA-256 архива и подготавливает `resources/git`.
Системный Git и PATH не изменяются. SSH-ключи, подтверждённый host key и права
на сервере настраиваются пользователем; HTTPS использует Git Credential Manager.
Исходные лицензии MinGit сохраняются рядом с его компонентами.

**Arkita** — самостоятельное приложение для Windows x64. Работа с моделями
локальная; браузер, сервер, Node.js и интернет для запуска и моделирования
не нужны. Mermaid-редактор «Схемка» в дистрибутив не входит.

## Сборка NSIS-установщика

Нужны Node.js 22.12+ и npm. Версии зависимостей закреплены в `package-lock.json`.

```sh
npm ci --ignore-scripts
npm test
npm run check
npm run package:win
sha256sum release/windows/Arkita-*-win-x64-setup.exe
```

Пакетирует electron-builder **26.15.3**, runtime Electron **44.10.2**.
Первой сборке нужен доступ к официальным загрузкам Electron, NSIS и
`electron-userland/electron-builder-binaries`. На Linux нужен Wine с поддержкой
WoW64 для генерации uninstaller; он не входит в приложение. На Windows Wine
не нужен. Для сборки на Linux используется Wine из официальных Ubuntu-пакетов; он
распаковывается в отдельный временный каталог без системной установки и
изменения сервисов. Рецепт ниже.
`npm ci --ignore-scripts` не загружает Linux Electron; для разработки через
`npm run desktop` отдельно выполните `node node_modules/electron/install.js`.
Windows-пакетирование само скачивает соответствующий Windows runtime.

### Изолированный Wine на Ubuntu 26.04

Этот build-only инструмент нужен для генерации NSIS uninstaller. Его префикс
не используется для запуска или приёмки Arkita. Пакеты загружает apt с обычной
проверкой метаданных; `dpkg-deb -x` только распаковывает файлы. Для одного
комплекта и префикса требуется около 3 GiB свободного временного места.

```sh
ARKITA_WINE_TOOLS=/tmp/arkita-wine-tools
mkdir -p "$ARKITA_WINE_TOOLS"
cd "$ARKITA_WINE_TOOLS"
apt-get download wine64=10.0~repack-12ubuntu1 libwine=10.0~repack-12ubuntu1 \
  wine-common=10.0~repack-12ubuntu1 libz-mingw-w64=1.3.1+dfsg-2
for package in ./*.deb; do dpkg-deb -x "$package" root; done
mkdir -p bin root/usr/share/wine/wine \
  prefix/drive_c/windows/system32 prefix/drive_c/windows/syswow64
ln -s ../root/usr/lib/x86_64-linux-gnu/wine/wine bin/wine
ln -s ../nls root/usr/share/wine/wine/nls
cp root/usr/x86_64-w64-mingw32/lib/zlib1.dll prefix/drive_c/windows/system32/
cp root/usr/i686-w64-mingw32/lib/zlib1.dll prefix/drive_c/windows/syswow64/
cd /srv/repos/arkita
PATH="$ARKITA_WINE_TOOLS/bin:$PATH" USE_SYSTEM_WINE=true \
  WINEPREFIX="$ARKITA_WINE_TOOLS/prefix" \
  WINEDATADIR="$ARKITA_WINE_TOOLS/root/usr/share/wine" npm run package:win
```

Использовать новый пустой каталог инструмента при повторной подготовке.
Symlink `wine/nls` воспроизводит ожидаемый Ubuntu loader путь; две zlib DLL
нужны соответствующим Windows-архитектурам в отдельном Wine-префиксе. Это
не изменение шаблонов NSIS или исходников упаковщика.

## Сборка portable EXE

После `npm ci --ignore-scripts` и проверок подготовьте Windows-приложение без
создания установщика. Для уже проверенного `release/windows/win-unpacked/`
эти два шага повторять не нужно:

```sh
node scripts/prepare-git.mjs
node node_modules/electron-builder/cli.js --win dir --x64 --publish never --no-config.win.signExecutable
```

Затем упакуйте этот каталог в portable EXE:

```sh
node node_modules/electron-builder/cli.js --win portable --x64 \
  --prepackaged release/windows/win-unpacked --publish never \
  --config.directories.output=release/windows-portable \
  --config.portable.artifactName='Arkita-${version}-win-${arch}-portable.${ext}' \
  --config.portable.useZip --no-config.win.signExecutable
sha256sum release/windows-portable/Arkita-*-win-x64-portable.exe
```

Эта команда использует штатный portable target electron-builder и подготовленные
файлы приложения. `useZip` обходит добавление elevation helper в этот каталог;
подпись отключена явно. Генерация деинсталлятора для portable не выполняется.
На компьютере пользователя EXE распаковывает приложение во временный каталог,
запускает его и убирает распакованные файлы после закрытия. Пользовательские
модели сохраняются в выбранной пользователем папке.

## Публикация дистрибутива

NSIS-установщик создаётся в `release/windows/`, portable — в
`release/windows-portable/`; `win-unpacked/` — промежуточный каталог для проверки
состава. В новом GitHub release с тегом `v<version>` после завершения проверок публикуется фактически собранный дистрибутив,
его SHA-256, версия исходников, результаты проверок и известные ограничения.
`--publish never` запрещает публикацию во время сборки; релиз публикуется
отдельно. Кандидаты публикуются как Pre-release по [правилам версий](VERSIONING.md);
существующие теги и файлы выпусков не заменяются. Автообновление и удалённое развёртывание не настроены.

`scripts/release.cjs` и `scripts/check-release.cjs` относятся к отдельной
Mermaid-сборке «Схемка» и не создают и не проверяют установщик Arkita.

Установка основного NSIS-варианта выполняется для текущего пользователя (`oneClick: true`,
`perMachine: false`), без выбора системного каталога и без elevation helper.
После установки приложение не запускается автоматически. Удаление не должно
удалять пользовательские модели; они сохраняются в выбранной пользователем
папке. Сборка не подписана сертификатом издателя: предупреждения Windows и
корпоративные политики проверяются в целевой Windows-среде и у тестировщиков отдельно.

## Что входит в приложение

В `resources/app.asar` входят Electron main/preload, модельные модули и их UI,
отдельная страница палитры, CLI, закреплённые Exchange XSD и notices/licenses.
Production dependencies `fontkit` **2.0.4** и `libxml2-wasm` **0.7.2** вместе
с их runtime dependencies поставляются для native контуров текста и offline
XSD-проверки. `fontkit` использует доступные системные шрифты Windows из
закрытого списка; дополнительный набор шрифтов не скачивается.
Точный состав задаёт `package.json` + lockfile и проверка распакованного ASAR.
Тесты, fixtures, Mermaid/vendor, каталог сервисов и private-data не поставляются.
Electron сохраняет собственные лицензии рядом с `Arkita.exe`; MinGit и его
лицензии находятся в `resources/git`.

Сетевые запросы renderer запрещены. Main выполняет только явно вызванные Git
операции; политика конкретного подключения поддерживает system/direct/manual
proxy для HTTPS. SSH и учётные данные управляются существующими системными
средствами. Внешняя HTTP/HTTPS ссылка после подтверждения открывается в
системном браузере. Node integration выключена; sandbox, context isolation
и web security включены. Custom protocol отдаёт только заранее разрешённые
локальные assets. Проверка ASAR headless не заменяет GUI-приёмку.

Установленный `Arkita.exe --cli` поддерживает `validate` и `export-csv` без
внешнего Node, с JSON-результатом и exit code. На Windows требуется дождаться
завершения GUI executable и перенаправить stdout; точные команды есть в
[описании CLI](AUTOMATION-AND-HOST.md#cli-из-установленного-приложения).

## Запуск и приёмка в Windows

Приёмку проводить по конкретному SHA-256 дистрибутива под обычной учётной
записью Windows. Сначала зафиксировать версию Windows, выбранный формат,
наличие предыдущей Arkita и контрольную сумму дистрибутива. Не использовать реальные модели
коллег для проверки аварийных сценариев.

1. Выполнить чистую установку NSIS без прав администратора; проверить запись
   в списке установленных приложений, ярлык в меню «Пуск» и открытие `.arkita`
   двойным кликом. Portable, если поставляется, проверить отдельно: прямой
   запуск, отсутствие установки, та же модель и кириллический путь.
2. Открыть Arkita выбранным способом. Проверить название и значок, читаемость панелей,
   меню и свойств, масштаб Windows 100% и 150%, окно и его минимальный размер.
3. Создать новую модель, добавить элементы и связь, изменить имя и описание,
   создать второй вид с общим объектом; проверить Undo/Redo.
4. Сохранить как `Проверка Arkita.arkita` в пользовательскую папку с пробелами
   и кириллицей. Изменить модель и нажать Ctrl+S: повторного выбора файла быть
   не должно. Закрыть, запустить снова и открыть файл; сверить виды, общие
   объекты, связи и свойства.
5. Передать копию файла второму тестировщику. Проверить открытие, изменение,
   сохранение под новым именем и повторное открытие этой копии.
6. Отменить открытие/сохранение и закрытие с несохранёнными изменениями;
   модель и история должны остаться. Сохранить во вторую копию и убедиться,
   что Ctrl+S обновляет именно выбранную копию.
7. На синтетическом файле после открытия изменить либо удалить файл вне
   Arkita. Ctrl+S должен показать конфликт и сохранить изменения в памяти;
   «Сохранить как» под другим именем должно сохранить копию. Гонку во время записи проверять отдельным синтетическим сценарием
   с readback сохранённых вариантов — см. ограничения ниже.
8. Для NSIS-варианта удалить приложение средствами Windows и повторить
   установку; для portable закрыть и снова запустить EXE. В обоих случаях
   проверить сохранность тестовых моделей и открытие сохранённой модели.

Записать результат каждого шага, версию/хеш дистрибутива и воспроизводимые
дефекты. Успешные Node/DOM-тесты или наличие `.exe` не означают прохождение
этих шагов.

## Критерии приёмки пакета 0.7.0 (историческая запись)

Выпуск включает изменения RC5 в завершении сохранения: проверить сохранения `.arkita`
и native-каталога с резервными копиями и без них. Проверить, что удаляются
только доказанные дубликаты текущей успешно завершённой операции. Для каталога
неканоническое форматирование прежних JSON-записей должно сохранить журнал.
Незавершённая запись, отказ записи, внешняя подмена и старые/неоднозначные
журналы сохраняют доступные уникальные байты и путь восстановления. Отказ
очистки оставляет успешное сохранение и предупреждение об оставшихся данных.
Это отдельная проверка от восстановления пользовательской копии в новый файл.

Для точного финального пакета 0.7.0 дополнительно проверить:

- Обновление установленной RC4 под тем же пользователем без предварительного
  удаления. До запуска зафиксировать тестовый профиль, настройки, недавние
  модели, Git-подключения и хеши моделей; после обновления сверить их сохранность,
  ассоциацию, полную версию в «Об Arkita» и открытие файлов.
- Сквозной сценарий: импорт Archi с отчётом и решениями → папки, общие объекты
  в нескольких видах, отношения и свойства → Undo/Redo → save/close/reopen →
  внешнее изменение и восстановление копии → Git-цикл в тестовом репозитории.
- Модель не менее 5000 native-записей: импорт, поиск, редактирование,
  Undo/Redo, сохранение, повторное открытие и Git; измерить время и память
  установленного приложения на контрольном Windows-стенде. Для большого списка
  изменений Git проверить переходы страниц, доступ к полям и полный Git-цикл.
- Холодное и повторное открытие `.arkita`, независимые окна и clipboard;
  тёмную/светлую тему, сохранённый явный фон и его сброс с Undo/Redo.

Смена RC на стабильную версию создаёт новый пакет. Нельзя переименовать EXE
кандидата или перенести его SHA/приёмку на финальный файл. Итоговые данные
и оставшиеся ограничения записываются для конкретного коммита и SHA-256.

## Базовые сценарии, добавленные в 0.6.0

К прежним сценариям [Windows acceptance](feature-corpus/WINDOWS-ACCEPTANCE.md)
добавляются отдельные окна моделей и их Undo/paths, duplicate-path focus,
OS association/second-instance/drop, восстановление стартового файла, размеры
окон/палитры и возврат на доступный монитор. Проверить перезапуск с настройками,
MRU, закрытие/порядок вкладок, резервную копию до перезаписи и recovery Save As.

Отдельные группы: перенос Cut/Copy между окнами через настоящий clipboard;
экспорт SVG/PNG/PDF и системная печать с масштабом/страницами; шрифты и кириллица;
offline Exchange XSD из ASAR; импорт с потерями и отменой; шаблоны и локальные
настройки; CLI из установленного EXE; встроенный Git с реальной авторизацией,
ошибкой сети и proxy. Физический второй монитор и принтер не считаются
проверенными через DOM, injected adapters или сохранение PDF.

Исторический статус находится в [реестре 0.6.0](feature-corpus/RELEASE-0.6.0.md).
Он не заменяет проверки текущего пакета; выбранный регресс и непроверенные
сценарии перечисляются отдельно в доказательствах нового выпуска.

## Границы поддержки

- Native writer — V4; V2/V3 открываются после проверки и миграции в памяти,
  затем требуют отдельный Save As. Исходный файл не переписывается миграцией.
- Есть CSV, Exchange XML и ограниченный Archi native XML 5.0.0 импорт с явным
  отчётом о потерях. Archi ZIP с ресурсами не поддерживается. XSD 3.1 Preliminary
  не доказывает эквивалентность нотаций или полное соответствие ArchiMate 4.
- Периодического автосохранения нет. Резервные копии перед перезаписью файла
  или каталога включены по умолчанию для новых настроек (1–20 копий модели);
  ранее сохранённое выключение сохраняется. «Файл → Резервные копии и
  восстановление…» позволяет найти копию по имени/пути и дате, затем восстановить
  её в отдельный новый `.arkita` файл. Существующие файлы, открытая модель и её
  история не изменяются. Это отдельный механизм от recovery-журналов
  незавершённой записи.
- Writer сохраняет before/after и фактически вытеснённые байты; при конфликте
  обычный Save останавливается. Требуется поддержка hardlinks. Это не файловая
  блокировка, не атомарная видимость multi-file каталога и не гарантия power loss.
  Один writer на модель остаётся поддерживаемым режимом. Успешное
  сохранение убирает только свой журнал с доказанными дубликатами: новая версия
  подтверждена сохранённой моделью, прежняя при перезаписи — проверенной резервной
  копией. Для native-каталога прежние JSON-записи должны побайтно совпадать с
  каноническим экспортом резервной копии; иначе журнал сохраняется. Старые,
  прерванные и неоднозначные журналы не очищаются. При отключённых резервных
  копиях журналы перезаписи остаются. Пользовательские копии управляются отдельно.
  [Native persistence](../electron/README.md),
  отдельный протокол сохранения байтов, не включённый в публичный исходный снимок.
- `UNKNOWN` не означает нормативного разрешения отношения. Дистрибутив
  не подписан сертификатом издателя; автообновление не настроено.

Справочники: [electron-builder NSIS](https://www.electron.build/v26/docs/nsis/),
[Electron security](https://www.electronjs.org/docs/latest/tutorial/security),
[ASAR](https://www.electronjs.org/docs/latest/tutorial/asar-archives).
