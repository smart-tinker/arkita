# Совместная работа через Git

Arkita использует обычный Git. Адресом сервера может быть GitHub, GitLab,
корпоративный Git-сервер или локальный репозиторий. GitHub API, аккаунт
Arkita и отдельный сервер совместной работы не нужны.

## Файл и репозиторий

`.arkita` — полный текстовый UTF-8 JSON-контейнер модели. Он содержит объекты,
отношения, представления, геометрию, свойства, профили, viewpoints, папки,
визуальные объекты и ресурсы. Это не ZIP и не изображение. Undo/Redo
и состояние редактора в него не входят.
Одинаковая модель сохраняется одинаковыми байтами. Файл можно коммитить
обычными Git-инструментами, однако вложенный JSON неудобен для просмотра
изменений и ручного объединения.

Встроенная совместная работа использует текущий формат native v4:

```text
arkita/
  schemka.json
  model/elements/el-<UUID>.json
  model/relationships/rel-<UUID>.json
  model/junctions/jct-<UUID>.json
  model/customization-profiles/prf-<UUID>.json
  model/folders/fld-<UUID>.json
  assets/ast-<UUID>.json
  viewpoints/vpt-<UUID>.json
  views/view-<UUID>/view.json
  views/view-<UUID>/occurrences/occ-<UUID>.json
  views/view-<UUID>/connections/conn-<UUID>.json
  views/view-<UUID>/visual-nodes/vnd-<UUID>.json
  views/view-<UUID>/visual-connectors/vcn-<UUID>.json
```

Имена каталогов и внутренние идентификаторы `schemka-*` — существующий
формат Arkita; отдельный Mermaid-проект «Схемка» здесь не участвует.
Переименование объекта не меняет его UUID или имя файла. JSON канонический:
порядок ключей и файлов стабилен, окончания строк LF. В native v4 свойства
хранятся как упорядоченный массив строк `{key, value}`; повторяющиеся ключи
и порядок строк сохраняются.

Модели native v2 и v3 при открытии преобразуются в v4 только в памяти.
Результат сохраняется через «Сохранить как» в отдельный файл `.arkita`
или новый каталог модели. Исходный файл или каталог остаётся неизменным.

Для модели выбираются адрес репозитория, ветка и каталог в репозитории.
По умолчанию каталог — `arkita`. Он принадлежит целиком модели; README,
документы и другие файлы следует хранить снаружи. Другие каталоги репозитория
не включаются в изменения модели. Для первого использования рекомендуется
отдельный небольшой репозиторий моделей.

## Рабочий процесс

Меню совместной работы открывает одно окно Git. Подключение само по себе
не заменяет открытую модель.

1. Подключить репозиторий и ветку. Существующую модель открыть явной командой
   и подтвердить замену текущей. В пустой каталог можно сохранить новую модель.
2. Редактировать модель. «Сохранить версию» создаёт локальный Git-коммит
   с описанием. Он доступен без сети.
3. «Отправить» отправляет сохранённые версии в выбранную ветку. Отказ сервера
   или отсутствие сети сохраняет локальные коммиты.
4. Перед получением изменений сохранить текущую версию. «Получить» загружает
   изменения и готовит объединение, которое применяется отдельно.
5. При пересечении правок выбрать для каждого объекта свою или удалённую
   запись. После выбора проверяется целостность всей модели. Нельзя принять
   результат с отсутствующими объектами, неверными ссылками или геометрией.

Автоматически объединяются изменения разных записей и одинаковые изменения
одной записи. Разные изменения одной записи и изменение/удаление требуют
выбора. Поля одной записи автоматически не смешиваются. Если независимые
изменения создают структурный конфликт, остаётся явный выбор целого снимка;
он отбрасывает изменения другой стороны и поэтому не выбирается автоматически.

Применение объединения той же модели — обычная отменяемая правка.
Undo/Redo, локальный файловый baseline и привязка `.arkita` сохраняются.
Первоначальное открытие из Git заменяет документ после подтверждения и
отвязывает прежний локальный файл, как обычное открытие другой модели.

Сохранить `.arkita`, сохранить локальную версию Git и отправить её на сервер —
три отдельные операции. Git-коммит не означает, что локальный `.arkita`
перезаписан. Отправка не включает более новые несохранённые в Git правки.

## Авторизация и хранение

Git использует пользовательские SSH-ключи, SSH-agent и настроенный менеджер
учётных данных. Пароль или токен нельзя вставлять в URL репозитория; Arkita
не хранит их в модели или своих настройках. Автор версии — имя и email из
настроек Git либо явно заданные в окне подключения. Они входят в Git-коммит.

Windows-установщик содержит официальный MinGit 2.56.0.2 x64. Отдельная
установка Git не нужна; системный PATH не меняется. Сборка загружает архив
из фиксированного upstream release, проверяет SHA-256 и заново распаковывает
его перед упаковкой. Лицензии и исходная структура MinGit сохраняются.
При запуске из исходников используется установленный Git.

Arkita хранит локальный bare-репозиторий в своём пользовательском каталоге.
Получение изменений не запускает checkout, фильтры модели, Git merge или
hooks и не перезаписывает открытый файл. Глобальные и системные настройки
Git считаются доверенными настройками пользователя: они могут запускать
настроенные credential helpers и SSH. Аргументы передаются без shell.

Разрешены HTTPS, SSH и абсолютные локальные адреса. Незашифрованный `git://`,
Git remote helpers, встроенные пароли, произвольные команды и force push
не предоставляются. Защита ветки и права пользователя на сервере продолжают
действовать. При неопределённом исходе отправки следует получить состояние
сервера: обрыв соединения сам по себе не доказывает отсутствие коммита на нём.

В первом варианте нет управления Pull/Merge Requests, блокировок объектов,
слияния отдельных полей, UI создания/удаления веток и одновременного онлайн
редактирования. Работа ведётся с одной выбранной моделью и веткой. Ограничения
модели остаются прежними: 8192 файлов, 256 КиБ на запись, 8 МиБ суммарно.
Размер истории Git отдельно этим ограничением не ограничивается.

При создании версии все проверенные записи передаются Git одним потоком
`fast-import` только как blobs с точным UTF-8 размером. Исходный текст модели
не становится командами. До построения дерева проверяются ID объектов
(SHA-1/SHA-256 исходных байтов), наличие, тип и размер. Создание commit и
обновление ветки с проверкой прежнего HEAD остаются отдельными действиями;
сам поток blobs не меняет ветки. Это убирает запуск отдельного Git-процесса
на каждую запись большой модели.

## Проверка

Изолированные проверки используют настоящие локальные bare-репозитории
и двух независимых клиентов: коммиты без сети, отправка, отказ при отставшей
ветке, получение, конфликтующие изменения, удаления, отмена и полная проверка
ссылок. DOM-проверки отдельно контролируют dirty/Undo, подтверждение открытия
и устаревшие ответы. Windows-установщик, реальный GUI, SSH/HTTPS и конкретный
сервер требуют отдельной приёмки; результаты фиксируются по версии артефакта.

coArchi не переносились.
